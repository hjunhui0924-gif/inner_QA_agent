# 真实浏览器用户体验走查（2026-09-27）

> 后续修复及验证见 [交互修复报告](interaction_recovery_implementation.md)。以下保留修复前的真实观察。

## 范围与结论

在提交 `5e7aa19` 上，通过 Playwright 实际点击 Chrome 140.0.7339.186 页面并检查截图，使用真实 DeepSeek v4 Pro 和独立 SQLite、Chroma、上传目录，没有模拟模型结果。操作包括：首页进入、上传文档、知识库首问及追问、查看引用、长回答等待与取消、等待中切换知识管理、草稿恢复、联网失败及重试、文档详情。共 7 次问答请求，其中 1 次主动取消。桌面 1440×900；手机尺寸 375×667（仅响应式视口，未覆盖真实手机软键盘）。

主要问题是长时间没有正文、等待时不能编辑草稿、取消后缺少恢复入口、手机错误操作被遮到对话滚动区下方。页面初始反馈很快，不能把全部等待归因于前端卡顿。此次仅走查、记录与定位，未修改产品代码。

## 优先处理的问题

### 1. 长回答的体感是长时间空等

复现：通用模式发送约 2000 字方案，21 s 截图中仍只有“正在处理你的问题”，到 24 s 取消前也没有正文。8 s 后有等待计时，20 s 后有“时间较长”提示，因此不是完全没有反馈；但正文区域和底部进度区域相距较远，用户盯着答案区容易认为没动静。短至 600 字的请求也要约 11.8 s 后才一次出现全文。

`frontend/src/utils/streamState.ts` 将 token 放入 `pendingContent`，只以 result 交付正文。这符合当前权威结果契约，不应直接把知识库候选 token 当正式答案展示。建议先把当前阶段、已等待时间及取消入口集中到答案占位区；明确区分“组织回答”和“校验依据”。如果希望通用模式逐字展示，应单独设计候选/正式结果契约，而非绕过知识库校验。

证据：[等待 21 秒](../work/ux-review/06-general-wait-21s.png)、[知识库等待状态](../work/ux-review/04-rag-5s.png)。

### 2. 等待期间不能提前编辑下一条问题

知识库和通用模式发送后，输入框立即 disabled，直到结果交付或取消。这会让 8–24 s 等待变成完全不可利用的时间。相关入口：`frontend/src/views/ChatView.vue` 的 textarea 使用 `sending || loadingHistory` 禁用。

建议允许继续编辑草稿，只禁用再次发送；收到答案后保留草稿。仍需限制并发提交，不意味着允许同时发多轮请求。

### 3. 取消后没有继续操作的快捷入口

取消后只显示“本次回答已取消”，输入框为空，没有“重新生成”或“编辑后重发”。原问题仍在对话里，但用户必须手动复制或重新输入。取消动作本身响应正常。

建议提供“重新生成”和“编辑问题”操作；恢复问题时不要覆盖用户已经新写的草稿。相关入口：`ChatView.vue` 的 cancelled 分支、`useWorkspace.ts` 的取消分支与 `retryMessage`。

证据：[取消后页面](../work/ux-review/07-general-final-or-cancel.png)。

### 4. 手机端错误卡片的操作落在可视区域之外

复现：375×667 新会话中发送联网请求，失败后等待 600 ms，页面已稳定；对话区仍 `scrollTop=0`、高度 333 px、内容高度 573 px。重试按钮顶部约 y=466，而对话可视区底部约 y=457，因此“重新发送”不在可见区域内。这时也没有出现“回到最新回答”提示，用户需要自己发现对话区可以滚动。

上方先显示一遍“联网服务不可用”的回答，下方错误卡片再次描述同一问题，进一步挤掉按钮。首次点击重试后追加第二组同样的问题和错误；旧重试按钮在发送期间看起来仍然可点（逻辑会忽略并发点击，未观察到重复并发请求）。

建议压缩重复错误文案，把恢复动作放在首屏可见区域；用户本来位于底部时，结果到达后正确跟随更新；用户主动上翻时则提供最新消息提示。定位线索：`ChatView.vue` 的内容 watch/滚动逻辑，以及 `useWorkspace.ts` 中保存原始 assistant 对象后直接修改它的方式，需后续用回归测试确认响应式触发问题。

证据：[稳定后的错误页面](../work/ux-review/23-mobile-error-settled.png)、[重复失败](../work/ux-review/16-mobile-retry-failed.png)。

### 5. 联网服务持续不可用时，恢复指引只有反复重试

本轮 3 次联网请求均返回不可用，页面正确拒绝编造来源。但错误卡片只建议“重新发送”，没有提供“关闭联网继续问”入口，也不说明这次失败和普通知识库服务是否有关。用户按指引操作后又得到相同错误。

建议提供明确的选择：“稍后重试”或“关闭联网，以通用知识回答”，后者必须由用户选择，不能静默冒充实时信息。供应商额度未恢复是既有外部问题，本条关注的是失败后的产品指引。

## 其他可改进项

- 手机展开“处理过程”后，对话阅读区从约 333 px 缩至约 183 px。进度列表有自己的滚动条，和对话滚动区相邻，阅读空间紧张。建议手机用可关闭面板，或只保留当前阶段并按需展开。[截图](../work/ux-review/12-mobile-progress-expanded.png)
- 等待中可以进入知识管理，任务继续且返回后状态能恢复；但管理页没有“回答仍在生成”的提示，用户离开后无法知道何时完成。[截图](../work/ux-review/08-navigation-during-answer.png)
- 上传不填写可选生效日期，列表和详情显示“1970-01-01 起”。这是默认边界值直接展示出来，容易被当成实际业务日期。后端上传默认值和前端日期格式化需一起明确“未指定”语义，不应只在页面把所有真实 1970 日期一律隐藏。[截图](../work/ux-review/21-knowledge-default-date.png)
- 首问多部分答案重复描述了一遍审批顺序，并把审批、材料和时限压成一个段落；阅读效率不如分条。属于本次模型输出观察，不能认定每次都会如此。[截图](../work/ux-review/05-rag-final.png)

## 正常表现与验证边界

首页入口清楚；上传有即时处理中提示；发送后立即有状态及取消按钮；8 s/20 s 等待提示生效；跨页后任务和草稿保留；知识问答与追问引用对应正确；桌面引用侧栏及手机引用面板可打开、关闭后焦点回到引用按钮。手机截图未见横向溢出。引用面板动画结束后文字清晰，初始过渡截图中的半透明叠影不列为缺陷。

首问监听未记录到 pageerror；没有对所有操作持续录制完整控制台，因此不声称全流程零控制台错误。没有进行真实手机键盘、弱网、断网或多人并发验证，也没有重跑整个自动化套件来代替体验观察。

本次操作脚本、截图和原始记录都在 `work/ux-review/`，测试服务仅使用隔离数据，走查结束后停止。后续建议先处理 1–4，再补服务失败指引与日期展示。
