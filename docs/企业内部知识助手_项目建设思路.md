# 企业内部知识助手：从原型到可评测 RAG 系统的建设思路

## 1. 我最终要解决的不是“做一个聊天页面”

项目最初可以被描述为一个基于 LangGraph、FastAPI、Streamlit 和 Chroma 的知识问答原型，但企业内部知识助手真正需要解决的问题并不是让模型“能够回答”，而是让回答具备以下性质：

1. 文档能够稳定接入，重复文件不会污染知识库；
2. 用户的不同表达、精确数字和制度原词都能被召回；
3. 回答可以追溯到具体文件、页码或章节和原文片段；
4. 证据不足、模型或外部服务异常时，系统能够安全拒答或降级；
5. 每一次优化都能通过固定数据证明，而不是依靠主观体验；
6. 失败能够被保存、分类并进入下一轮优化。

因此，我把项目目标从“完成一个 RAG Demo”重新定义为：

> 建立一条从文档接入、知识治理、混合检索、证据化生成到自动评测和失败归因的闭环，并让每个关键技术选择都有可验证的理由。

Streamlit 在当前阶段继续作为 Web 演示前端。项目的核心风险集中在知识治理、检索和回答可信度，而不是页面框架；在后端接口和交互模式尚未稳定前重写前端，投入产出比不高。

## 2. 总体推进顺序

我没有先堆叠模型和 Agent 节点，而是按照“先保证数据正确，再优化检索，最后约束生成”的顺序推进：

```mermaid
flowchart LR
    A[明确企业问答的可信目标] --> B[检查文档解析与元数据]
    B --> C[设计切块和两层去重]
    C --> D[确定 Embedding 与索引身份]
    D --> E[建立 BM25 与向量双路召回]
    E --> F[RRF 融合与 Rerank 精排]
    F --> G[带引用生成与失败关闭]
    G --> H[固定权威语料和评测集]
    H --> I[消融实验与答案评测]
    I --> J[失败归因并回到对应环节]
```

这套顺序的关键在于：如果解析、切块或索引已经错了，再强的生成模型也只能基于错误上下文作答；如果只看最终回答，则无法区分问题究竟来自召回、排序、生成还是引用。

## 3. 第一步：先检查原始架构，确定改造边界

项目保留了原有的分层结构：

- LangGraph 负责编排路由、检索、相关性判断、查询改写、生成和幻觉检查；
- FastAPI 提供上传、对话、历史记录和 SSE 流式接口；
- Chroma 持久化向量索引；
- SQLite 保存对话状态和用户记忆；
- Streamlit 提供可直接演示的 Web 页面。

我优先改造的是 RAG 内核，而不是推倒重写整个项目。生产检索对上层只暴露稳定的 `retrieve(query, top_k)` 接口，内部则可以切换 `dense`、`lexical`、`fusion` 和 `rerank` 四种策略。这样既避免检索实现渗透到 Agent 节点，也使消融实验可以复用同一份业务代码。

## 4. 第二步：先治理知识，再讨论模型效果

### 4.1 文档解析与位置元数据

企业问答的引用不能只返回一个文件名。PDF 按页保存 Segment，Markdown 和 DOCX 按标题保存 Section；切块和写入 Chroma 后继续保留文档 ID、标题、来源、文件名、页码、章节和稳定 Chunk ID。

这样设计有两个目的：

- 用户可以从回答回到原始制度位置；
- 评测程序可以判断引用的摘录是否真的来自对应 Chunk。

### 4.2 切块选择

当前默认 `chunk_size=800`、`overlap=120`。切块优先尊重段落和句子边界，只有内容过长时才硬切。

选择这一方案的原因是：

- Chunk 太小，会把条件、例外和结论拆散，检索虽然命中关键词，却缺少完整证据；
- Chunk 太大，会引入过多无关内容，增加 Embedding 表达噪声和生成上下文成本；
- 保留一定重叠，可以降低关键句恰好落在边界上的风险；
- 先按自然段和句号切分，比固定字符窗口更适合中文制度文档。

800/120 不是永远正确的参数，而是当前法规语料上的工程起点。它们被写入索引和评测元数据，后续可以通过实验调整，而不是成为不可追踪的魔法数字。

### 4.3 为什么去重不使用 Embedding

去重与语义检索的目标不同。语义相近不代表文档重复：两份制度可能讨论同一个主题，却在适用范围、金额或例外条件上不同。如果使用 Embedding 相似度直接删除，很容易把真正需要保留的制度误判为副本。

因此我采用两层去重：

1. **精确去重**：对 Unicode、大小写和空白规范化后的全文计算 SHA-256；
2. **近重复去重**：对足够长且长度接近的文档计算字符 5-shingle 覆盖率，默认阈值为 0.92。

短文本只做精确去重，因为短文本的 shingle 相似度波动过大。近重复还要求长度比例至少达到 0.85，避免一份摘要被误认为完整制度副本。

这套方案刻意偏保守：宁可暂时保留一份可疑文档，也不应静默删除一份可能包含不同规则的正式制度。

## 5. 第三步：选择 Embedding，并管理索引生命周期

### 5.1 候选方案

Embedding 选择不能只看模型榜单，还要结合中文语料、部署方式、成本、依赖和索引维护：

| 方案 | 优点 | 当前没有作为默认方案的原因 |
| --- | --- | --- |
| `text-embedding-v3` | 中文语义能力、DashScope 托管、维度可配置、与现有调用体系一致 | 需要网络和 API 配额 |
| 本地 BGE-M3 等模型 | 数据可完全本地化，适合强隐私场景 | 增加模型下载、显存、推理服务和部署维护成本 |
| 旧版或更弱的通用 Embedding | 迁移成本低 | 没有足够理由继续使用能力和配置灵活性更弱的模型 |
| Hashing Embedding | 离线、确定性、测试速度快 | 本质是词法特征，不具备真正的语义泛化能力 |

### 5.2 最终选择

项目默认使用 DashScope `text-embedding-v3`，维度为 1024；Hashing Embedding 只用于离线开发和自动化测试，不进入正式评测或生产结论。

选择 `text-embedding-v3` 的原因是：

1. 当前主要语料为中文法规和企业制度，中文语义召回是首要需求；
2. 项目已经使用 DashScope 的生成和排序服务，复用认证和网络体系可减少运维复杂度；
3. 1024 维在当前规模下兼顾表达能力、存储量和检索成本；
4. 托管服务使项目可以把精力放在检索链路、引用和评测，而不是额外维护一个 Embedding 推理服务；
5. 项目保留统一 Embedding 适配层，未来有数据本地化要求时可以替换为本地模型。

### 5.3 避免新旧向量混用

Embedding 模型、维度或预处理发生变化后，旧向量不能继续混在同一个 collection 中。系统把 provider、model、dimensions 和 index version 共同计算成 Chroma collection 身份。任何一项变化都会生成新的 collection 名称。

这一步解决的是一个常被忽略的工程问题：模型已经升级，但程序仍然查询旧索引，最后无法判断效果下降来自模型、索引还是数据。

## 6. 第四步：从单路向量检索升级为四段式检索

### 6.1 为什么不能只用向量检索

向量检索适合同义表达和自然语言改写，但企业制度中有大量需要精确匹配的信息，例如文号、日期、比例、金额、岗位名称和法律原词。只依赖向量相似度，可能找到主题相近的条款，却错过包含精确答案的段落。

反过来，只用 BM25 又难以处理用户口语化表达和同义改写。因此两者不是互相替代，而是解决不同类型的召回问题。

### 6.2 BM25 + 向量 + RRF + Rerank

最终检索链路为：

1. **BM25 式词法召回**：保留中文连续词、二元和三元片段，负责精确词和数字场景；
2. **向量召回**：使用 `text-embedding-v3` 处理语义相近表达；
3. **RRF 融合**：根据两个候选列表的排名融合，不直接混合量纲不同的 BM25 分数和向量分数；
4. **Rerank 精排**：使用 `gte-rerank-v2` 对有限候选进行 Query-Document 相关性重排。

RRF 默认 `k=60`，词法和向量权重各 0.5。两个通道的候选使用稳定 Chunk ID 去重。Rerank 只处理融合后的前 12 个候选，以控制远程调用延迟和成本。

### 6.3 为什么选择 RRF，而不是直接加权分数

BM25、向量相似度和不同模型返回的分数没有统一量纲。直接写成 `0.5 * BM25 + 0.5 * cosine` 看似简单，实际上权重会受到语料规模、分数范围和模型版本影响。

RRF 只依赖排名位置，可以在不做复杂分数校准的前提下稳定融合异构召回结果，也方便解释每个候选分别来自哪个通道和处于什么名次。

### 6.4 为什么仍然需要 Rerank

召回阶段追求“不要漏”，精排阶段追求“把最能回答问题的证据放到前面”。`gte-rerank-v2` 能联合理解 Query 和候选原文，比单独比较向量更适合区分主题相近、条件不同的条款。

代价是延迟上升，因此系统设置超时和失败降级：Rerank 不可用时直接返回 RRF 结果，并记录 `degraded_reason`，而不是让整个问答失败。

## 7. 第五步：让回答具备证据，而不只是“像正确答案”

生成时，每个候选 Chunk 被赋予 `[C1]`、`[C2]` 等引用编号。模型被要求让事实、数字、日期和规则带引用，并尽量只回答问题本身，避免额外补充未经引用覆盖的背景信息。

最终结构化引用包含：

- 文档 ID、标题、来源和原始文件名；
- 页码或章节；
- 稳定 Chunk ID；
- 对应逐字原文摘录；
- `verification_status=provenance_only`。

我特意把引用状态定义为 `provenance_only`。程序可以确定摘录来自某个 Chunk，但“原文是否在语义上支持回答”不能仅靠字符串检查证明。语义支持由独立的幻觉检查或自动 Judge 负责。

### 安全失败策略

- 没有直接证据时明确拒答，不引用无关 Top-K；
- 引用编号越界、关键数字冲突或引用缺失时不静默放行；
- 生成模型异常时返回安全失败信息，不把检索片段拼成一个伪答案；
- 生产幻觉 Judge 不可用时失败关闭；
- SSE 最终事件返回最终答案、结构化引用、Trace ID 和失败类型，避免页面展示与后端最终状态不一致。

## 8. 第六步：建立可信、可复现的评测数据

为了避免只用几段自造文本证明效果，我选择了主题相近、容易互相干扰的官方文档：

- 中国人大网《中华人民共和国个人信息保护法》；
- 中国人大网《中华人民共和国数据安全法》；
- 国家互联网信息办公室《生成式人工智能服务管理暂行办法》；
- 中国政府网《网络数据安全管理条例》。

下载过程保存来源 URL、发布机构、抓取时间和正文 SHA-256，并校验最终域名和正文长度。这样可以证明评测语料来源可靠，也可以发现网页内容发生变化。

当前正式开发集有 34 题，其中 30 题可回答、4 题无答案，覆盖定义、日期、数字、条件、精确规则和相似条款。它适合做开发阶段的消融和回归，但由于参与过调优，不能被描述为独立留出集或生产 SLA。

## 9. 第七步：用消融实验决定方案，而不是凭感觉选组件

我在完全相同的语料、切块、Top-K 和问题上，分别运行四种策略：

| 策略 | Source Hit@5 | MRR@5 | 完整证据命中率 | P50 延迟 |
| --- | ---: | ---: | ---: | ---: |
| 向量检索 | 100.00% | 91.78% | 86.67% | 245 ms |
| BM25 式词法检索 | 96.67% | 92.78% | 86.67% | 0.6 ms |
| BM25 + 向量 + RRF | 100.00% | 93.89% | 96.67% | 183 ms |
| BM25 + 向量 + RRF + Rerank | 100.00% | 95.00% | 100.00% | 671 ms |

这些数据说明：

- Dense 和 BM25 都能解决对方不擅长的样本；
- RRF 把完整证据命中率从 86.67% 提升到 96.67%；
- Rerank 进一步把完整证据命中率提升到 100%，MRR 提升到 95%；
- Rerank 的收益伴随明显延迟，因此保留故障降级，而不是假设远程服务永远可用。

这也是最终默认启用四段式检索的依据。如果未来换成另一批企业文档后 Rerank 不再有稳定收益，就应根据新数据关闭，而不是为了技术栈完整而保留。

## 10. 第八步：从检索评测扩展到答案和引用评测

检索命中不代表最终答案可信，所以我又增加了答案级 Benchmark。它对每个问题执行检索、一次 `qwen3.6-plus` 生成和一次自动 Judge，并同时计算确定性代理指标：

- 参考事实短语匹配；
- 数字和日期匹配；
- 引用摘录是否来自对应 Chunk；
- 事实句是否带引用；
- 回答与引文的抽取重合；
- 无答案问题是否正确拒答。

自动 Judge 严格要求返回 JSON；缺字段、类型错误、解释文字包裹 JSON、网络异常或解析失败都会标记为 unavailable，并按失败关闭处理。生成模型和 Judge 分别通过 `MODEL_NAME` 与 `JUDGE_MODEL_NAME` 配置，当前都使用 `qwen3.6-plus`，为将来切换不同模型交叉评判预留接口。

当前 34 题结果为：

- 自动 Judge 回答正确：100%（34/34）；
- Grounded：94.12%（32/34）；
- 引用语义支持：94.12%（32/34）；
- 正确拒答：100%（34/34）；
- 四项全部通过：94.12%（32/34）；
- 数字/日期匹配、引用出处准确率和引用完整性：100%。

这里不能把“同模型自动 Judge 的 100%”写成人工确认准确率。它是开发阶段数据，用于持续比较版本，不是对任意企业语料的泛化承诺。

## 11. 第九步：保留失败样本，形成优化闭环

最终没有为了让报告变成 100% 而修改评判标准。剩余两个失败样本的核心回答正确，但模型额外补充了岗位资质信息，同时引用只覆盖资质，没有覆盖“必须设置负责人和管理机构”的核心义务条款。

这类失败说明，Source Hit@5 为 100% 仍不等于回答完全 Grounded。它可能来自：

1. 切块把同一条法规的义务和资质拆开；
2. Rerank 把只包含补充信息的 Chunk 排得更高；
3. 生成模型回答了问题未要求的内容；
4. 引用选择没有覆盖回答中的全部断言。

线上 Trace 和评测报告会保存问题、召回 Chunk、答案、引用、节点轨迹和失败类型。出现问题后，先判断是解析失败、召回失败、排序错误、生成错误、引用错误还是拒答错误，再回到对应模块优化。这避免了所有失败都通过修改 Prompt 解决。

## 12. 工程化收尾

为了让项目不仅能演示，还能被维护和验证，我补齐了以下工程约束：

- 集中配置模型、检索候选数、超时、切块和去重阈值；
- 模型名等关键配置启动时校验，禁止空值静默回退；
- 上传大小、最大解析字符数、PDF 页数和压缩包解压大小限制；
- 知识库写入锁，降低并发写入破坏数据的风险；
- Trace 默认关闭，并设置容量轮转和 Git 忽略；
- Partial、远程失败或生成异常的评测不会覆盖正式报告；
- 单元测试覆盖检索融合、降级、引用、配置、去重和自动 Judge；
- 每次对外声称完成前运行全量测试、编译检查、报告契约断言和 `git diff --check`。

本轮最终验证结果为 `83 passed, 2 skipped`，后端、脚本和 Streamlit 前端均通过 Python 编译检查。

## 13. 最终形成的闭环

项目最终形成了三层闭环：

### 数据闭环

文档解析 → 元数据保留 → 切块 → 精确/近重复去重 → Embedding 索引身份 → 可更新知识库。

### 问答闭环

用户问题 → 路由/改写 → BM25 与向量召回 → RRF → Rerank → 带引用生成 → 幻觉检查 → 安全回答或拒答。

### 评测闭环

固定权威语料 → 检索消融 → 答案与引用评测 → 自动 Judge → 失败归因 → 定位对应模块 → 重新回归。

到这里，项目的价值不再只是“使用了 LangGraph、RAG 和 Chroma”，而是能够说明：为什么选择这些组件、每个组件解决什么问题、它带来了多少收益、失败时如何降级，以及如何用数据判断下一步是否值得继续优化。

## 14. 当前边界与下一阶段

当前系统可以作为企业知识助手作品集、受控政策问答 Demo 和后续生产化的技术基础，但仍有明确边界：

- 34 题是开发集，规模不足以证明跨领域生产效果；
- 生成与 Judge 当前使用同一模型，存在自评偏差；
- 尚未完成部门级权限隔离和完整文档版本管理；
- Streamlit 适合演示，不是最终企业前端；
- 表格、扫描 PDF 和复杂版式仍需要更强解析能力。

下一阶段如果继续投入，优先级应是独立留出集、跨模型 Judge、权限隔离和文档版本生命周期，而不是继续针对当前 34 题追求表面上的 100%。
