# 企业知识助手产品体验与性能优化实施方案

> 日期：2026-09-26。状态（2026-09-27 更新）：M1–M5 代码已实现，功能回归通过；M6 真实性能/质量联合验收及完整浏览器矩阵尚未全部通过。详见 product_experience_implementation_report.md。
> 用户确认：**1A：页面及任务入口分离，保留现有开发身份；2A：优化已有知识管理功能，不新增文档编辑、删除、替换及版本切换。**
> 交付目标：统一产品首页、问答工作台和知识管理的视觉与交互；同时改善操作流畅度、真实答案交付耗时和等待体验。

## 1. 执行原则与文档优先级

1. 本文是本轮新增体验设计、范围和验收的执行规格；真实接口以当前代码及契约测试为准。发现冲突，先记录并修正规格，不能伪造接口实现页面。
2. 当前运行配色以 `frontend/src/styles/tokens.css` 为事实基线：浅灰白、钴蓝、中文系统无衬线字体。
3. `docs/frontend_optimization_implementation_plan.md` 含较早的森林绿风格及已经解决的问题；`design-system/enterprise-knowledge-assistant/MASTER.md` 仍有森林绿和外部字体内容。不能据此把本轮界面改回旧版。
4. 开发基础模块时同步更新上述文档的适用状态和设计规范，保留历史记录，避免两份互相冲突的有效规格。本文生成阶段不改历史记录或应用代码。
5. 一个模块实现、测试、验收通过后再开发下一个模块。失败必须修复或明确阻塞，不能以“后续统一处理”绕过验收。
6. 产品功能变化、延迟数据和竞品观察分别记录。竞品是参考方向，不是功能契约；本次未成功在线核验国内竞品最新界面，不声称完成竞品实测。

## 2. 产品定位、用户与范围

### 2.1 定位与成功标准

定位：面向企业员工的知识问答助手，帮助用户查询制度、流程和业务资料，并通过原文引用核对回答；为知识维护人员提供独立的资料维护入口。

核心路径：进入工作台 → 提问 → 得到正式答案 → 按需核对原文 → 继续追问。

产品首页帮助首次访问者理解价值；管理页帮助维护人员完成任务，不占据员工问答的主要注意力。通用问答保留，但不与企业知识问答争夺首页主定位。

### 2.2 用户与任务

| 用户 | 主要任务 | 本轮呈现 |
|---|---|---|
| 首次访问者、面试或项目评审者 | 理解产品并开始体验 | 产品首页、明确的工作台入口、标注为示例的问答预览 |
| 员工使用场景 | 提问、读答案、核对依据、查看历史 | 问答工作台、引用面板、来源详情与已有下载能力 |
| 知识维护场景 | 上传、查找、筛选、查看文档信息 | 独立知识管理布局，保留现有元数据能力 |

这些是**任务场景划分**，本轮不声称实现真实用户角色分流。同一开发身份可以访问两个工作区，不新增假登录页、角色切换器或账号系统。

### 2.3 本轮必须完成

- 新增简洁产品首页，支持直接访问问答工作台。
- 分离问答布局与知识管理布局；共用品牌和组件规范。
- 空会话输入优先、答案阅读优化、引用逐步披露。
- 现有文档上传、筛选、详情、下载的视觉和反馈优化。
- 统一动效、键盘操作、减少动态效果和移动端行为。
- 真实状态驱动的等待体验；前后端延迟测量与有证据的热点优化。
- 核心回归、浏览器验收、截图、性能前后对照及开发文档更新。

### 2.4 明确不在本轮

- 企业 SSO、账号密码登录、真实员工/管理员界面授权和多租户。
- 文档编辑、删除、替换、版本回滚、批量管理、审批和连接器。
- 新增对话内附件、指定文件集合提问、跨库选择、完整资料门户。
- 未校验候选答案实时展示、模型供应商迁移、默认移除校验或降低检索质量。
- 深色主题、多语言、独立移动 App、付费套餐、虚构客户案例和统计看板。

基线来自本轮源码读取，非运行测试结果；不能将历史测试通过数量当成本轮通过数量。

特别说明：引用面板并非当前默认固定展开；本轮解决的是空入口、引用上下文和展开后的密度问题。内联引用、焦点管理、移动抽屉等已有能力应保留并改进，不能列作从零新增。

## 4. 页面与导航结构

### 4.1 路由与布局

| 路径 | 新职责 | 布局与进入策略 |
|---|---|---|
| `/` | 产品首页 | 独立 LandingLayout；公开静态介绍，不加载会话与知识数据 |
| `/chat` | 问答工作台 | ChatLayout；会话导航、消息区、输入区、按需证据 |
| `/knowledge` | 知识管理 | ManagementLayout；品牌、工作区导航、管理内容，不显示会话列表 |

可用 Vue Router 路由 meta.layout 选择布局；只实例化活动布局。App 保留全局 Toast、路由出口及必要可访问性基础，工作区初始化移入对应布局。

- 首页主按钮“进入问答工作台”指向 `/chat`；次按钮“了解使用方式”滚动到本页介绍。
- 问答侧栏主要是“新对话”、会话搜索和历史；“知识管理”放次级工作区入口。
- 管理页明确提供“返回问答”。品牌链接回首页，不能意外清空当前会话。
- 不通过首次访问 localStorage 自动跳转首页；两个地址行为稳定、可收藏。
- 保留 `/knowledge`，避免旧链接失效。部署必须正确回退 SPA 路由，验证直接打开和刷新。
- 本轮不实现刷新后自动恢复特定会话的新深链接协议；保留原有历史加载路径，不宣称新增持久化恢复。

### 4.2 路由切换与请求生命周期

- 在同一 SPA 内切换业务页，保留当前消息、模式和未发送草稿；返回后恢复该会话阅读位置，不强制滚到底部。
- 在每个会话切换时独立保存草稿与滚动位置；删除会话时清理对应 UI 缓存。仅保存在内存，不新增敏感草稿持久化。
- 回答进行中可进入知识管理；请求归工作区状态管理，不能因 ChatView 卸载而丢失处理。页面返回显示真实当前状态。
- 保留现有同一时刻只能发送一轮、不能在进行中切换/删除会话的约束；不要通过隐藏旧页面绕过限制。
- 引用、详情等临时抽屉离开所属页面时关闭；返回不会自动弹出。
- 初始化采用可重试状态；失败后不能被 initialized 永久挡住。并发初始化复用 in-flight promise，避免重复请求。

## 5. 产品首页规格

### 5.1 内容顺序

1. 顶部：现有品牌“内部知识助手”、本页能力锚点、“进入工作台”。不在本轮更名。
2. 首屏：标题建议“让企业知识，成为有据可查的答案”；补充一句说明；主要 CTA；可见的产品界面预览。
3. 场景：查制度、理流程、核对依据，最多三项，使用简短具体问题。
4. 使用方式：添加资料 → 提问 → 阅读答案与来源。说明添加资料属于维护场景。
5. 产品特点：企业资料问答、引用原文、文档信息维护；不把已有版本字段称为完整版本管理。
6. 页尾：再次进入工作台；简短说明重要事项需核对原文。

### 5.2 预览与素材

- 优先使用与真实组件视觉一致的轻量静态界面预览；明确显示“示例问答”，样例来源为合成资料。
- 示例答案必须与示例原文逐句相符；无需请求真实模型，不自动播放真实请求或上传资料。
- 可提供一次“查看示例来源”交互；局部面板变化，不循环闪烁、不模拟虚假生成百分比。
- 不使用竞品商标截图作为自己的产品界面，不虚构客户、使用人数、准确率或认证。
- 主体不超过约 4～5 个内容区，避免长篇营销；真实工作台体验优先于首页装饰。
- 后端不可用时首页仍正常可读；点击进入工作台后再按实际情况报告连接异常。

### 5.3 响应式与性能

- 桌面可采用文案与预览双栏；窄屏单栏，CTA 不被预览挤出主要阅读区域。
- 不使用大视频背景、外部字体阻塞、重型三维场景。预览保留尺寸，图片采用合适尺寸和懒加载。
- 首页组件与业务页面按路由拆包；首页不导入整个知识库/会话状态来取得静态文案。

## 6. 问答工作台规格

### 6.1 空会话

- 一级内容仅保留一句引导、输入框、最多三个推荐问题。详细产品介绍移到首页。
- 输入框靠近主要视觉中心；低高度屏幕优先保证输入和发送按钮可见，不强制垂直居中。
- 推荐问题用紧凑按钮或轻卡片放输入框下方；点击填入草稿并聚焦，不自动消耗模型额度。
- 企业知识库模式默认选中，通用模式保留；第一问后模式锁定，切换需新建会话。
- 已有通用模式与联网搜索语义保持不变；不能把内部知识和互联网来源混为同一种依据。
- 输入提示不暗示未实现的附件、选库或指定文件能力。

### 6.2 开始对话

- 提交后立即显示用户消息和处理状态，清空已提交草稿，阻止重复提交。
- 输入框切换到底部；共用同一份草稿和事件逻辑，不维护两套 textarea 业务状态。
- 有动效时使用稳定最终布局加 transform/opacity 过渡；不每帧修改 grid 高度，不在中文输入法组合期间误提交。
- 保留 Ctrl/Cmd+Enter 发送、Enter 换行；增加 composing 保护，不未经说明更改已有快捷键。
- 字数上限保持当前 12000；超限或空白输入有明确反馈，按钮状态与真实可发送状态一致。

### 6.3 答案阅读

- 答案采用文档排版，正文 16px、行高约 1.75～1.9，阅读列最大宽度 760～800px。
- 用户消息保留轻气泡；助手正文减少大块背景，标题、列表、表格、代码和链接有明确层级。
- 长表格和代码块局部横向滚动，不能撑宽整个页面。
- 保留安全 Markdown、DOMPurify 和 URL 白名单；不能为了动画改为不受控 v-html 内容。
- 正式答案收到后立即完整可读，不做逐字重播。复制内容只来自正式答案。
- 自动滚动仅在用户靠近底部时发生；上翻后提供“回到最新回答”，不抢焦点。

### 6.4 状态与异常

| 情况 | 页面行为 |
|---|---|
| 刚发送、尚无服务端事件 | 本地“正在连接服务…”；不能声称已开始检索 |
| 收到 status | 按真实节点显示用户可理解的一行状态；详细过程可展开 |
| 处理较久 | 保留当前阶段，显示已等待时长及取消入口；不编造完成百分比 |
| result 成功 | 提交正式内容及引用，结束答案等待状态 |
| result 带 failure_type | 显示真实 fallback 内容及对应失败说明，不当作网络中断 |
| 无 result 就结束/断开 | 传输错误，不暴露 pendingContent；按现有规则支持重试 |
| result 后断开 | 保留已交付答案，不能回退成失败或取消 |
| 用户取消 | 立即响应；无结果时标记取消；已交付结果保持；不承诺上游计费立即停止 |
| 后端离线/鉴权失败 | 说明实际问题，避免所有业务错误统一显示为“网络断开” |

等待提示默认在 8 秒后增加“仍在处理，可继续等待或取消”，20 秒后提示“本次处理时间较长”。这些是 UI 提醒阈值，不是超时预算，不触发自动重试，也不推测当前内部阶段。

## 7. 引用与来源：按需披露及上下文绑定

### 7.1 展示层级

1. 正文保留 `[C1]` 等可操作引用，键盘可访问。
2. 回答下方保留一条紧凑入口，例如“查看 3 条引用”；仅少量标题概览，不重复整行长文件名卡片和多次数量提示。
3. 点击编号或入口后打开原文详情，定位对应引用。无引用时不渲染空入口。

“引用条数”直接取 citations 数量；不能把多个同文件片段当成多个文档计数。如展示来源文件数，按 source_id/document_id/URL 去重，无法稳定识别时只显示引用条数。

### 7.2 UI 状态设计（新增前端状态，不是后端字段）

使用独立 evidenceSelection，包含：sessionId、messageId、citationId、citationsSnapshot、triggerElement。消息标识优先使用持久 message_id，旧历史回退到本次加载稳定的 UiMessage.id。

- 引用编号只在该条回答内唯一；选择键必须带消息和会话，不能用 C1 作为全局主键。
- 新答案完成或新问题发送，不覆盖用户正在核对的旧答案引用。
- 切换会话、删除所属消息/会话或离开页面时关闭；禁止将旧文档显示为新回答依据。
- 新增问题仍在同一会话时，保留用户主动打开的旧证据，显示对应回答的简短上下文。
- 关闭面板后焦点返回真实点击来源，不统一返回顶部按钮；触发器失效时回到关联消息，再回到输入框兜底。
- 不将 DOM 引用持久化到 localStorage 或业务接口；面板离开后清理监听和计时器。

### 7.3 面板布局

- 视口至少 1280px、且扣除侧栏约 248px、证据约 340px 后仍有至少 600px 主内容空间时，采用并排面板。
- 其余尺寸采用右侧模态抽屉；手机占满或接近满宽。CSS 与 JS 断点使用同一规则，避免视觉与模态语义错位。
- 并排模式不锁主内容焦点；模态模式使用现有 overlay 栈，背景 inert、Tab 循环、Escape 关闭、焦点回收。
- 面板标题“引用来源”，内容按文档标题 → 原文 → 位置信息 → 可用操作 → 校验说明排序。
- 位置只有存在时显示页码/章节；引用类型当前没有 version 字段，不能直接假定存在。需要版本信息时，仅在 source_id 有效且已授权详情返回对应字段后显示。
- 当前 source_id 对应详情可能代表更新后的资料，不能将现行文档版本反向声称为历史回答当时使用的版本。快照版本追溯放后续方向。
- 网页来源使用现有 URL 和 web_source 标识；没有 quote 时不展示“复制原文”，不伪造网页正文。
- 只能复制已有原文或打开已有合法来源；404/403 分别提示不存在/无权访问，不显示技术堆栈。

## 8. 知识管理：只优化已有能力

### 8.1 列表与筛选

- 页名“知识管理”；主操作“添加文档”；保留文档数量及已生效数量，说明统计基于当前可访问列表。
- 现有客户端关键词、部门、状态、版本筛选继续复用，不宣称全库服务端全文搜索。
- 文档名称 14～16px；常用辅助信息至少 12px；标签不使用 10px 小字。
- 名称、部门、版本、生效状态是主要比较信息；原文件名、来源、日期范围、负责人为辅助信息。
- 桌面紧凑列表，手机按行堆叠关键信息；避免桌面字段全部压缩成微小文字。
- 保留刷新、空库、无匹配结果、加载失败与重试状态。后台刷新有旧数据时保留旧列表并标记刷新中。
- 现有字段不含可信更新时间时，不新增“最近更新”列或相关排序。
- 本轮不新增后端分页或批量操作；使用至少 100 条 fixture 检查列表与筛选体验，超出规模时记录后续分页/虚拟化需求。

### 8.2 上传

- 右侧抽屉保留拖拽/文件选择、文件信息、移除和上传动作。
- 文件类型、大小限制从现有前后端契约读取；不在不同页面硬编码不同限制。
- “文档信息与生效设置”继续默认折叠，保留当前表单字段和 internal 上传范围。API 支持的其他 ACL 字段继续兼容，但本轮不把它们扩展成新的权限配置表单。
- 保留必填校验、重复提示、失败重试；失败保留所选文件和填写内容。
- 当前 fetch 上传接口没有字节进度或后端入库进度事件。本轮显示不定进度“正在上传并处理文档”，禁止虚构 30%/80% 或“正在向量化”等无事件支撑的阶段。
- 返回成功后刷新列表并突出新文档；重复返回时定位已存在项，不虚增文档数量。
- 上传进行中允许关闭抽屉，但后台状态归工作区持有；重开显示真实状态，禁止二次提交。新增 uploadTask 内存状态保存本次 File、提交元数据快照、结果及错误；路由切换后仍可恢复提示，结束后释放不再需要的 File 引用。页面刷新可能中断请求，不能承诺后台任务持久执行。

### 8.3 详情与下载

- 只读详情保留标题、现有元数据、正文或预览、来源下载。
- 详情加载和下载分别反馈；关闭抽屉或切换文档时忽略过期响应。
- 下载失败不清空详情；来源授权继续由后端执行。
- 不出现编辑、删除、回滚、设为生效等未实现按钮，包括不可用占位按钮。

## 9. 视觉与动效规范

参考组合：ima 的轻量提问组织、飞书的企业信息层级、语雀的中文阅读、FastGPT/MaxKB 的任务与管理结构。仅借鉴原则，不复刻品牌；如开发期间取得真实截图，将观察和取舍补充进实现报告。

### 9.1 基础视觉

| 项目 | 规格 |
|---|---|
| 背景/面板 | 保留 #F8F9FC / #FFFFFF，侧栏 #F3F5F9 |
| 强调色/正文 | 保留 #3458CF / #202634；危险、警告、成功分别用语义色 |
| 字体 | 复用系统中文无衬线栈，不下载外部字体 |
| 字号 | 正文 16px；控件 14px；辅助 12～13px；工作区标题 24～30px；首页标题 32～48px 自适应 |
| 间距 | 4/8px 基础，常用 8/12/16/24/32；页面空间按场景调节 |
| 圆角 | 控件 8px；卡片和输入面板 12～16px |
| 阴影 | 基础面板低强度，浮层增强；不为每行文档加阴影 |
| 触控/焦点 | 主要交互目标至少 44×44px；可见焦点；正文正常对比度至少 4.5:1 |

在 tokens.css 中补齐字号、间距和 motion token；避免各组件复制硬编码。首页可更有展示感，工作台安静，管理页更紧凑，但按钮与状态语义一致。

### 9.2 动效规格

| 场景 | 默认时长 | 方式与限制 |
|---|---|---|
| 按钮悬停、按下、输入聚焦 | 120～180ms | 色彩、边框、轻微位移；不改变布局尺寸 |
| 抽屉展开关闭 | 200～240ms | transform + opacity；关闭后卸载时机与焦点回收协调 |
| 证据选中 | 约 1000ms | 一次背景/描边高亮，之后恢复；焦点状态持续可见 |
| 空会话切入对话 | 180～220ms | 最终布局先稳定；必要时 FLIP，避免克隆出两个可聚焦输入框 |
| 首页首屏 | 240～360ms | 轻微淡入与位移，仅一次，不阻止 CTA 点击 |
| 列表更新 | 120～180ms | 仅受影响的行提示，不让整页反复入场 |

- 优先 CSS transition、Vue Transition/TransitionGroup；不默认引入 GSAP 或全站动画库。
- 不使用 transition: all，不连续动画 width/height/top/left，不无期限添加 will-change。
- prefers-reduced-motion 下移除位移、平滑滚动和装饰循环，状态变化立即可见；加载语义仍保留。
- 不以动画时长延迟 API 调用、输入解锁或答案显示。关闭动作和取消操作始终立即响应。
- 动画中重复点击、快速开关和切换路由不能产生残留遮罩、双重滚动锁或重复提交。

## 10. 同时优化操作流畅与回答耗时

### 10.1 先建立可复现测量

新增浏览器本地测量工具与独立基准脚本，复用现有 trace_id/turn_id 关联，不把调试指标直接展示给普通用户。

| 指标 | 定义 |
|---|---|
| T_feedback | 用户提交到本地可见反馈的时间 |
| T_first_status | 发起请求到首个服务端 status；无 status 的重放单独归类 |
| T_result | 发起请求到收到权威 result，不以 token 首字代替 |
| T_visible | 发起请求到正式答案完成首轮 DOM 绘制 |
| T_ready | 发起请求到可以发下一轮；必须与 T_visible 分开 |
| T_session_refresh | 会话列表请求自身耗时，不计成模型生成耗时 |
| 后端阶段耗时 | 上下文、路由、检索、重排、相关性评估、生成、校验、持久化、标题；重试记录次数 |

前端使用 performance.now/mark/measure 和绘制时点；后端使用单调时钟。同名阶段多次执行保留序号或累计值，区分墙钟时间与各段求和，不能跨机器直接相减。

当前 Trace 总耗时及模型计数可复用；阶段字段为拟新增内部指标，不增加必需的 SSE 字段。运行日志默认不记录问题正文、答案和原文；指标保留有限条目并可清理。

### 10.2 必须处理的具体热点

**A. 首页及业务页初始化**

- 首页不发 health/sessions/knowledge 请求。
- 问答页只加载必要健康状态和会话；知识列表进入管理时加载。
- 健康状态不是功能请求的永久闸门，支持明确重试。保留 401/403 与网络异常区分。
- 在现有 useWorkspace 内先提取可复用加载职责，不为当前规模强行引入 Pinia。

**B. 会话刷新不阻塞发送状态**

- SSE 正常完成或交付结果后中断，先完成发送状态清理，再非阻塞刷新列表。
- 为 loadSessions 增加请求代次，过期返回不得覆盖较新的列表、当前会话删除或新会话状态。
- 列表刷新失败只影响侧栏提示，不把已完成答案改成失败。
- 本轮保留串行问答约束；不能仅收到 result 就放开第二个未结束的流。result 后尽快发送 done/结束响应，不把标题或持久日志拖在流尾。

**C. 标题摘要移出答案关键路径**

目标是保留模型摘要标题能力，同时让首次答案交付不等待标题模型。

1. 先完成现有答案和历史持久化，使用现有确定性标题回退建立会话，再交付 result/done。
2. 在响应结束后由应用管理的后台任务生成首问摘要；不得创建无人管理的 fire-and-forget 协程，也不得继续占用本轮 session_operation 锁等待模型。
3. 新增内部 title task 管理模块；按 user_id + session_id 去重，初始并发上限 2、等待队列上限 32、单任务超时 10 秒、max_retries=0。溢出/失败保留可用回退标题，不影响问答。
4. 标题任务只依据第一问；任务完成后在会话操作锁内确认会话仍存在、首问标识匹配，再执行条件更新。删除后不得 upsert 复活会话；后续追问不能重命名。
5. 应用 shutdown 取消并等待任务结束，释放资源；本轮队列为单进程尽力执行，重启丢失待处理任务时仍有回退标题，不宣称持久任务系统。
6. 标题调用使用独立计时和预算，不修改已经交付的 result.budget_snapshot；报告单独列出后台调用成本，并计入总体成本对照。
7. 当前 `backend/api/routes.py` 的 chat_sessions 会等待旧标题模型回填，`backend/agent/memory.py` 提供候选查询与存储。GET 会话列表不得同步调用模型。改成读取立即返回、同一任务管理器限量入队待处理标题；已成功/失败记录与冷却策略避免每次 GET 重复付费。优先新会话，旧标题回填每次最多 2 条，失败冷却至少 10 分钟；进程内已成功摘要但恰好与原问题相同的标题也应标记完成，防止反复回填。
8. 前端保持现有 sessions 响应结构，先用回退标题；本次首问结束后若工作台仍可见，可在 2/5/10 秒做最多三次后台刷新。切换任务、卸载、删除或新请求后取消旧计时器，不永久轮询；标题仍未更新也不阻止使用。

上述是拟实现方案，须增加后台任务及删除竞态测试。若现有存储结构无法可靠判断首问，需要先完成最小存储迁移及兼容测试，不能退化成无条件 upsert。

**D. 其余推理热点按测量选择**

- 检查重复模型/检索客户端构建、可复用连接、无依赖 I/O 串行、重复读取与不必要的大上下文。
- 只并行真正独立的操作；检索、筛选、生成、校验、提交的依赖不能为提速而打乱。
- 本轮默认保持模型、候选数、重排、校验和请求预算配置。只有质量对照证明不退步时，才纳入进一步局部优化。
- 不直接加跨用户答案缓存。若测量显示确需缓存，先定义 ACL、资料版本、生效状态、模型及失效边界，作为独立后续任务。
- 完成 A/B/C 和测量后，若没有更多可安全优化热点，提交证据即可；不能为了达到百分比指标牺牲正确性。

### 10.3 等待体验与传输契约

- 后端 `status` 来源是真实图节点；现有 UI 可归纳为理解问题、查找资料、整理回答、核对依据，但没有收到相应事件时不提前显示。
- 状态事件不保证每个固定阶段都会出现；允许跳过、重试、拒答和直接返回。
- 前端 token 仍不作为正式答案；当前后端虽在提交后发 token，但接口未承诺所有未来实现的 token 都可直接展示。
- 拆分已有安全最终答案不应逐块 sleep；不要用“打字机效果”延长已经完成的回答。
- SSE 代理缓冲、连接取消传播及关闭时机需要通过真实链路核查；仅前端 mock 无法证明这些问题已解决。

### 10.4 性能目标与测量条件

以下为本轮目标，不是已达成数据，也不是所有网络环境的服务承诺。

- 标准桌面环境下 T_feedback P95 ≤ 100ms；若 CI 无法可靠测量，保留本机性能 trace 和机器信息。
- result 收到到正式答案首次绘制 P95 ≤ 150ms，测试答案长度固定；超长 Markdown 单独测试与报告。
- 正常 SSE 结束到发送按钮恢复 P95 ≤ 100ms，与 sessions API 人工延迟 5 秒无关。
- 默认动效期间不得出现本次变更导致的明显长任务；以 Performance trace 检查超过 50ms 的任务并归因，不以“看起来 60fps”作为唯一证据。
- 首页本地生产预览固定环境、冷缓存 5 次记录 LCP/CLS；参考目标 LCP ≤ 2.5 秒、CLS ≤ 0.1，记录设备、网络模拟、浏览器和构建版本。
- 真实模型 T_result 按首次问答、追问、联网、拒答分别比较；首次问答的标题阻塞必须消除。总体 P50 改善 15% 为争取目标，不能无基线承诺秒数；任何未达成或 P95 回退均解释归因，不隐藏失败样本。

## 11. API、数据与兼容边界

前端默认前缀 `/api`，由 VITE_API_BASE_URL 覆盖；下面为现有路径，不新增登录、编辑、删除文档等接口。

| 方法及路径 | 用途 | 关键约束 |
|---|---|---|
| GET `/health` | 服务健康 | 不等同模型回答质量或全系统就绪证明 |
| POST `/chat/stream` | 问答 SSE | message/user_id/session_id/mode/web_search/turn_id 保持兼容 |
| GET `/chat/sessions/{user_id}` | 会话列表 | 返回 items；移除同步标题生成，不改变结构 |
| GET `/chat/history/{user_id}/{session_id}` | 历史 | 保留引用及失败元数据 |
| DELETE `/chat/session/{user_id}/{session_id}` | 删除会话 | 保留历史和 checkpoint 完整删除；后台标题不能复活 |
| GET `/knowledge/records` | 可访问资料列表 | 返回 items，权限过滤由服务端完成 |
| GET `/knowledge/records/{source_id}` | 详情 | 返回 record；权限再次校验 |
| GET `/knowledge/records/{source_id}/download` | 下载 | Blob/文件响应，不绕过授权 |
| POST `/knowledge/upload` | 上传 | FormData；保留现有字段与重复判断 |

- SSE 事件名仍为 status/token/result/done，result.content 为正式内容。
- failure_type、failure_stage、failure_reason、trace_id、turn_id 保持既有语义；未知错误安全降级，不新增没有后端依据的错误枚举。
- 同 turn_id 重放与“用户主动再试一次”不同：主动重试创建新 turn_id，不能让旧结果重放掩盖重试。
- 前端 user_id 目前为开发上下文固定值，不把它作为可信身份。后端仍验证路径身份和 ACL。
- 禁止把内部路径、上游错误正文、密钥、trace 原始内容带入 UI。
- 本轮新增的布局、证据选择、等待计时、性能记录属于前端或内部观测状态，不混入后端业务响应。

### 13.4 延迟与答案质量对照

新增 `scripts/benchmark_chat_latency.py` 时提供 `--help`，固定配置文件或命令参数，支持输出 JSON/CSV 到 work。不能在未实现前声称该脚本可执行。

拟定最小 CLI 契约：`--base-url` 为包含实际 API 前缀的地址，`--cases` 指向冻结案例 JSON，`--repeats` 默认 3，`--output-dir` 为隔离输出目录，`--live` 必须显式开启远端模型调用。新增案例文件 `tests/fixtures/chat_latency_cases.json`，包含 case_id、场景类别、mode、web_search、messages；每个案例每次运行创建全新 session_id，各轮创建新 turn_id，追问仅在该案例内部共享会话。JSON 保存逐轮原始指标及失败分类，CSV 保存统计摘要；不默认写正文或凭证。

基准使用专门的隔离后端与固定语料，不能向生产会话灌入测试问题。纯 HTTP 脚本只能测量传输时点；T_feedback/T_visible/T_ready 由浏览器脚本补充，不能用 HTTP 收到 result 的时间冒充页面已经绘制。

- 固定至少 20 个案例：8 个知识问题、4 个追问链案例、3 个资料不足/拒答、3 个通用问题、2 个联网问题；追问保留相同前置历史。
- 每例至少运行 3 次。首问/追问分组，重放命中不混入普通速度统计；冷启动、暖态和远端网络波动分开标记。
- 前后采用同语料快照、权限身份、模型及参数、设备和浏览器。交替或相邻批次运行，避免只比较不同时段的远端负载。
- 报告分组样本数、P50/P95、成功率、超时率、模型/工具调用和成本；小样本 P95 标明探索性，不当长期 SLA。
- 所有失败保留计数与耗时，不能只统计成功样本而隐藏更高失败率。
- 校验事实、条件/例外完整性、引用与陈述对应、拒答正确性、追问版本继承；模型 Judge 仅辅助，不当独立质量证明。
- 任一权限泄露、未校验候选展示、引用错配、已交付答案回退，立即停止该模块交付。新出现的事实/引用错误不得以延迟改善抵消。
- 没有足够真实运行证据时，“真实耗时优化验收”仍未完成；可以交付代码及测量工具，但报告必须标出阻塞条件。
